## Developer path

From a clean Windows or Linux checkout, a real Hermes installation at the pinned release (`v2026.8.3`, commit `3c27eb6`) loads the minimal repository-root Shim (`hermes_shim/`) from a real source install into an isolated `HERMES_HOME`, where the install fixture's default HEAD is pinned to the Candidate SHA; a PluginManager probe proves the load and exact registration counts; the Shim registers `hermes pipeline setup|doctor|start|status|stop` and a `pre_gateway_dispatch` hook, bootstraps the fake managed runtime from the dedicated `runtime-env/` project (FastAPI/Uvicorn inside the isolated runtime environment under accepted ADR-0028; the runtime entry lives only under `src/hermes_pipeline/transport/`), and delivers one authenticated loopback fake command exactly once — the three crash points produce no forged or lost acknowledged result, a synthetic Feishu-style `/card` probe event is intercepted without ever invoking Prod Main, and the complete canonical check set plus the Hermes probe suite pass offline on Windows and Linux.

## Must scope (READY, revision 5)

- **Shim surface and code placement.** Add the repository-root Hermes plugin entry: `plugin.yaml` (name `hermes-software-pipeline`, version matching package metadata, `kind: standalone` or omitted, no `requires_env`, `manifest_version` at most 1) and root `__init__.py` that imports **only** the controlled root directory `hermes_shim/` and never imports `src/hermes_pipeline`. `hermes_shim/` is stdlib-only and registers: the `pipeline` CLI command tree (`setup`, `doctor`, `start`, `status`, `stop`) via `ctx.register_cli_command`, the `pre_gateway_dispatch` hook, and one minimal declared high-level tool. `src/hermes_pipeline/cli/` is **not** a 00-05 writable path. The shim contains no Controller logic, no Agent executor, no Git, no database, no network beyond loopback, and no runtime-dependency import (ADR-0019, ADR-0026, `ci-and-testing.md` runtime rule); an import scan enforces it.
- **Never-raise, never-forward hook.** The `pre_gateway_dispatch` callback must never raise; any event whose text belongs to the shim's fake-probe namespace is answered with `{"action": "skip", "reason": …}` **unconditionally — including when the runtime is unreachable** — so a probe event can never fall through to Prod Main; all other events are left untouched (`None`). A probe event that reaches Prod Main is a failure of this scope.
- **Fake managed runtime and runtime locking topology.** Under `src/hermes_pipeline/transport/` only (the runtime entry is launched by the shim as an independent interpreter with a **controlled argv array**, never a shell string): loopback-only binding (`127.0.0.1`/`::1`), `/livez`, `/readyz`, `/v1/version`, `/v1/commands` with bearer-token authentication, protocol-version header, strict Host/Origin validation, body-size and rate limits, and timeouts. The server implementation is FastAPI/Uvicorn, authorized **only** by accepted ADR-0028. **Executable locking topology (fixed under accepted ADR-0028)**: a dedicated runtime project at repository root `runtime-env/` with its own `pyproject.toml` and committed `runtime-env/uv.lock`. Its direct dependencies include `fastapi`, `uvicorn`, and `hermes-pipeline==0.1.0`; `[tool.uv.sources] hermes-pipeline = { path = "..", editable = false }` makes that explicit root-package dependency install into the runtime environment, so `python -m hermes_pipeline.transport` resolves **without any `PYTHONPATH` manipulation**. A cross-platform provision harness, not a shell wrapper, creates a sanitized child environment with `UV_PROJECT_ENVIRONMENT=<fresh-state-root>/runtimes/<version>` and runs the controlled argv `[uv, "sync", "--frozen", "--project", "<repo>/runtime-env"]`; it proves `sys.prefix` and the launched interpreter are that exact state-root environment, not `runtime-env/.venv`. The interpreter is `<state-root>/runtimes/<version>/Scripts/python.exe` (Windows) or `…/bin/python` (POSIX), resolved per platform; the runtime entry is `[<interpreter>, "-m", "hermes_pipeline.transport", "--state-root", <path>, …]`; the root project `[project].dependencies` stays empty and the root `uv.lock` is untouched. The runtime descriptor is written atomically (temp + rename) with owner-only ACL/mode and PID, start identity, creation time, port, token generation, release, and state-root identity; the state-root singleton lock is acquired at startup; any startup-step failure leaves the runtime not-ready; no file paths, shell commands, SQL, or raw exceptions cross the HTTP surface.
- **Fixed protocol values.** Host header must equal `127.0.0.1:<port>` or `[::1]:<port>` (else `400` + `POLICY_REJECTED`); Origin must be absent or exactly `http://127.0.0.1:<port>` / `http://[::1]:<port>` (else `403` + `POLICY_REJECTED`); protocol header `X-Hermes-Pipeline-Protocol: 1` required (missing/unsupported → `400` + `VALIDATION_ERROR`, fixed message `unsupported protocol version`); bearer token from the descriptor (bad/missing → `401` + `AUTHENTICATION_FAILED`); body limit 64 KiB on `/v1/commands` (exceeded → `413` + `VALIDATION_ERROR`); rate limit one client window of 60 seconds with at most 60 requests (exceeded → `429` + `RATE_LIMITED`); shim client connect/read timeout 5 s, runtime request budget 10 s; unknown path → `404` + `NOT_FOUND`; stale/absent descriptor at the client → `DEPENDENCY_UNAVAILABLE` (shim fails closed); `/v1/version` reports runtime version, protocol version `1`, contract-schema range, release, and state-root identity.
- **Descriptor/protocol versioning (fixed, not a human option).** The descriptor and loopback protocol are versioned inside the spike as **versioned constants plus golden JSON fixtures** (a golden descriptor fixture and a golden `/v1/version` response fixture with committed accept/reject vectors). The committed JSON Schema / contract-toolchain path (`src/hermes_pipeline/contracts/`, `schemas/`) is out of scope for this Slice.
- **Runtime lifecycle, recovery, and identity.** `start` bootstraps the managed environment per the fixed runtime-env topology, launches the runtime, waits for readiness, and writes the descriptor; `stop` drains, releases the lock, and removes the descriptor. **Token rotation happens only when the runtime process starts** (start, restart, or crash recovery); a Hermes-process restart merely re-reads the existing descriptor and token — it never rotates and never rewrites the descriptor. **Stale-descriptor algorithm (cross-platform)**: every runtime start records `pid`, a fresh random `start_identity` (128-bit hex), and the process creation time; a descriptor is stale and removable only when `os.kill(pid, 0)` reports the process gone, **or** the creation time mismatches (Linux `/proc/<pid>/stat` field 22; Windows `ctypes` `kernel32.OpenProcess`/`GetProcessTimes` — PID reuse detected); a live matching process means the descriptor is never removed; `os.kill(pid, 0)` alone is never proof of identity. Port collision: at most 3 consecutive attempts, each a fresh random loopback port; after 3 failures the runtime exits with `DEPENDENCY_UNAVAILABLE` and leaves no descriptor. `status`/`doctor` never block beyond the client timeout.
- **Fake command exactly-once with three crash points.** The fake runtime accepts one fake Controller-command envelope (`command_id` + payload) and persists a receipt with stdlib `sqlite3` in the disposable state root (fixed D4); a duplicate `command_id` returns the original receipt. Crash points: (A) **before persistence** — no receipt row, no ack; retry with the same `command_id` processes afresh with exactly one receipt and one effect; (B) **after persistence, before the response** — retry returns the original receipt (dedup), no second effect; (C) **after the response** — the shim holds the receipt and does not resend; any transport retry still dedups to the original receipt. A forged receipt (not matching the persisted row) is rejected. The store and its data are disposable spike artifacts with an explicit disposition and never become production persistence.
- **Windows descriptor ACL — exact ACE set.** Explicit DACL applied and verified with `icacls` (controlled argv subprocess, never a shell string): **exactly one grant ACE for the current user (resolved user SID) with `(F)` full control, and nothing else**. Application: `icacls <path> /inheritance:r /grant:r <user-sid>:(F)`. Verification parses `icacls <path>` output and must show **only** the current-user SID with `(F)`; any other subject — `Everyone` (`*S-1-1-0`), `BUILTIN\Users` (`*S-1-5-32-545`), `SYSTEM` (`*S-1-5-18`), `BUILTIN\Administrators` (`*S-1-5-32-544`), or any other — appearing in the descriptor DACL fails verification. Negative fixtures with an `Everyone:(R)` ACE or a `SYSTEM:(F)` ACE are rejected. Residual limit: verification covers the descriptor DACL only; a local administrator or SYSTEM can still access the file through host-admin mechanisms **outside** the DACL (take-ownership, backup semantics) — the documented host-admin boundary of the threat model, not permitted ACEs inside the DACL. POSIX uses `0o600` plus a mode check.
- **Synthetic `/card` interception probe.** With the shim loaded in a real Hermes process, construct the Feishu-style synthetic event exactly as the installed Feishu adapter does (`/card <tag> <json>`, `MessageType.COMMAND`, resolved source) and drive the real gateway dispatch path (`GatewayRunner._handle_message`); the hook must skip the probe event and submit one authenticated loopback fake command; a Prod Main invocation counter stays at zero; the probe tag is namespaced (for example `hermes_pipeline_fake_probe`) and no other `/card` or plain event is intercepted.
- **Load and registration evidence (PluginManager probe).** `hermes plugins list` proves manifest/enable state only and is never used as load evidence. A subprocess running the Hermes environment's Python with an isolated `HERMES_HOME` calls `get_plugin_manager().discover_and_load()` and asserts: `loaded.enabled is True`, `loaded.error is None`, **exactly one tool, exactly one `pre_gateway_dispatch` hook, exactly one top-level `pipeline` CLI command, and exactly five `pipeline` subcommands** (`setup`, `doctor`, `start`, `status`, `stop`). A deliberately broken plugin fixture asserts `loaded.error` is set and Hermes keeps running (fail-safe load).
- **Real source-install evidence with Candidate-identity binding.** The integration workflow defines `HERMES_PIPELINE_CANDIDATE_SHA` as `github.sha` for `push` and `github.event.pull_request.head.sha` for `pull_request`, then checks out that exact SHA before any probe. In CI on both platforms, the install fixture is a **temporary local Git fixture whose default HEAD is pinned to that exact Candidate SHA**: (1) assert `git rev-parse HEAD == HERMES_PIPELINE_CANDIDATE_SHA`; (2) `git clone --no-checkout <repo-path> <fixture>`; (3) `git -C <fixture> checkout -B main <HERMES_PIPELINE_CANDIDATE_SHA>`; (4) pre-install assertions that fixture `rev-parse HEAD` equals the Candidate and `symbolic-ref HEAD` equals `refs/heads/main` (the SHA, not the branch, is evidence); (5) `hermes plugins install file://<fixture> --enable` into an isolated `HERMES_HOME`; (6) post-install assertion that the installed checkout `HEAD` equals the Candidate and that `HEAD^{tree}` equals the tested Candidate tree. A fixture whose `main` points at a non-Candidate SHA must fail the post-install assertion. All Git argv is controlled; writes are confined to the temporary fixture directory and the repository's own Git state is untouched. Load and registration are additionally proven by the PluginManager probe. No public network is used after dependency bootstrap; no credentials; no real Feishu/GitHub/business operation.
- **Lifecycle CLI idempotency (EC-00-11).** `hermes pipeline setup|doctor|start|status|stop` operate idempotently for the non-production skeleton: repeated identical invocations converge; `stop` without a running runtime is a no-op with a stable exit code; `doctor` fails with actionable codes when a required version/descriptor/state-root component is missing; all commands return structured bounded JSON with stable exit codes. The state root is derived from `HERMES_HOME` (`<HERMES_HOME>/software-pipeline/`, fixed D5).
- **Negative and adversarial evidence.** Deterministic negative tests for: bad token, wrong protocol version, stale/absent descriptor, malformed descriptor, descriptor path escape (symlink/junction/reparse-point), owner-only descriptor ACL on both platforms (Windows: the exact single-ACE set above), body-size and rate-limit exceedance, Host/Origin mismatch, loopback-only binding, environment/secret leakage (injected secret canaries must never reach the runtime environment, logs, receipts, or the Execution Report), port collision (≤3 retries), double-start lock contention, and descriptor DACLs containing an `Everyone` or `SYSTEM` ACE.
- **Reproducible Hermes provision, environment authority, and CI design.** The Hermes provision is pinned: clone `https://github.com/NousResearch/hermes-agent` at the exact release commit `3c27eb6234bf91b8ceee9e9071591b31e9b148cb` (tag `v2026.8.3`), build with **Hermes' own `uv.lock`** (`uv sync --frozen` inside the Hermes checkout) into an **independent Hermes test environment** outside this repository's `.venv`. Network is allowed only during dependency bootstrap: this-repository checkout, the pinned Hermes clone, Hermes environment build, and the first frozen `runtime-env/` materialization; all probes and the second runtime materialization are then offline. Every child process starts from an empty mapping rather than inherited `os.environ`. The provision child may receive only resolved executable/system essentials (`PATH`, platform-required `SystemRoot`/`ComSpec` or `HOME`, and a test-owned temp/cache directory), `UV_PROJECT_ENVIRONMENT`, and `PYTHONDONTWRITEBYTECODE=1`; the runtime child additionally receives only its test-owned state-root inputs; the Hermes probe child additionally receives only isolated `HERMES_HOME`, resolved `HERMES_PIPELINE_PROBE_HERMES`, `HERMES_PIPELINE_CANDIDATE_SHA`, and `PYTHONDONTWRITEBYTECODE=1`. Values are derived by the fixture, no parent environment mapping is copied, and an injected unknown-secret canary must be absent from every child and bounded report. Probes locate Hermes through the explicit variable and invoke it with controlled argv arrays; `uv run --offline pytest` does **not** assume Hermes exists in the project dev environment – probe suites skip with a clear reason when the variable is absent and fail (not skip) when it is set but broken; in required CI the variable is always set. One new workflow (`.github/workflows/hermes-integration.yml`) runs the probe suite on Windows and Linux; the existing `python-quality.yml` and `documentation-contracts.yml` stay untouched.
- **Workflow governance (fixed technical scope of this Slice — not a separate human decision).** The existing `--check-workflows` checker covers exactly the two existing workflows (`scripts/check_documentation.py:604-752`) and does not cover `hermes-integration.yml`; the READY revision extends `scripts/check_documentation.py` with a `check_hermes_integration_workflow` rule set — strict YAML-subset parse; `on:` exactly push/pull_request; `permissions: {contents: read}`; no `secrets:` context; job matrix covers `ubuntu-latest` and `windows-latest`; pinned action versions; the exact offline probe command inventory of the probe job; a network-cutoff boundary comment marker — plus positive and negative workflow fixtures under `scripts/fixtures/workflows/`, and the verification commands `workflow-policy-hermes` (positive) and `workflow-policy-hermes-negative` (negative fixtures must fail).
