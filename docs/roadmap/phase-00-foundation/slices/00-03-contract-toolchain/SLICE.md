## Developer path

From a clean Windows or Linux checkout, install the frozen Python 3.12 development environment once. The committed JSON Schemas, the OpenAPI document, and the compatibility registry are generated deterministically from the versioned Pydantic authoring types; `contracts check` fully validates the registry (identity lock, Draft 2020-12 meta-validation with `FORMAT_CHECKER`, baseline corpus agreement, canonical hashes) offline, and `contracts drift-check` proves the committed projections still match generation exactly by generating into a temporary directory and comparing read-only.

## Revision 6 clarification

`/v1` remains a single semantic contract. There is no divergence allowlist between a JSON Schema and its Pydantic authoring type. “Strict” forbids coercion from strings, booleans, and incompatible primitive categories; it does not contradict Draft 2020-12's integer semantics, under which a finite integral JSON number such as `3.0` satisfies `type: integer`. The authoring model must therefore accept that value while rejecting non-integral numbers and cross-primitive coercion. The frozen `jsonschema` installation lacks its optional RFC 3339 checker, so the toolchain must register one deterministic checker on `Draft202012Validator.FORMAT_CHECKER`, sharing the authoring type's validation rule. This fulfills—not relaxes—AC-03 and AC-05.

## Out of scope

- Controller business behavior, HTTP service, database, persisted Events, LangGraph, Hermes Shim, Agent, browser, or any real external call;
- FastAPI or any service framework; OpenAPI generation that requires a new framework or a dependency family beyond ADR-0026;
- direct hand-editing of generated Schemas, the OpenAPI document, or the compatibility registry (edits are drift-check failures; changes go through the Pydantic source);
- runtime dependencies: `[project].dependencies` remains empty; Pydantic/JCS execution in the Hermes plugin entry, `--version`, or the normal runtime path would need a separate runtime-installation and isolation design ADR/Slice;
- real migrations, storage, or business state for the compatibility registry;
- recomputing `content_hash` in historical planning, review, evidence, or closeout records;
- any Slice 00-04, 00-05, or 00-06 behavior.

## Interfaces and authority

- Authoring source: `src/hermes_pipeline/contracts/` Pydantic v2 authoring types (13 root contracts plus the `common/definitions` `$defs` type library) are the sole source for `schemas/*.schema.json`, `contracts/openapi.json`, and `contracts/compatibility-registry.json`; generated files are never edited independently. Strict model validation must preserve the f36 Schema pass/reject boundary, including coercion-sensitive cases such as integral `3.0` JSON numbers for integer Schema fields; a divergence allowlist is forbidden.
- `contracts check` — full read-only validation; keeps its Slice 00-02 exit semantics (0 pass, 1 fail) and gains meta-validation, corpus, and canonical-hash coverage; the toolchain is lazy-imported only after the `contracts` subcommand is parsed; a bounded error is returned when development dependencies are absent.
- `contracts generate` — development-only write command that updates the committed projections from the models.
- `contracts drift-check` — read-only zero-drift gate that generates into a temporary directory and byte-compares with the committed files; used by CI.
- Baseline evidence: `tests/fixtures/contracts/` contains immutable f36 Schema snapshots and a raw-digest manifest; the baseline validator builds its complete reference registry only from those snapshots and never relies on a runtime Git object lookup, current generated Schema, or network access.
- OpenAPI component keys: for every `$id` `https://schemas.hermes-pipeline.dev/{namespace}/{resource}/v{n}`, the component key is PascalCase(namespace) + PascalCase(resource) + `V` + n; the 14 fixed mappings are enumerated in AC-07.
- OpenAPI component values: each fixed component embeds the full corresponding generated Schema object, including its exact `$id`; external references or placeholder objects are rejected, and canonical component content must equal the matching generated Schema.
- Compatibility registry structure: a JSON object mapping each registry `$id` to `{current_version: integer >= 1, supported_versions: non-empty strictly increasing integer array with current_version as its maximum}`; the key set must equal the 14-Schema `$id` set exactly.
- The Pydantic models, generators, jsonschema, and `rfc8785` are imported only from uv development/CI commands after the `contracts` subcommand is parsed; the Hermes plugin entry, `--version`, and the normal runtime path never import them (enforced by a regression test). A deterministic RFC 3339 checker is registered on `Draft202012Validator.FORMAT_CHECKER` using the same shared rule as the authoring type; no new dependency family or Schema/model divergence is accepted.
- The Executor may read every tracked file but may edit only the machine contract's permitted paths in the assigned worktree.

Revision 6 enforcement for the remaining criteria:

- `AC-05`: use a snapshot-only 14-Schema registry; the three authorities must agree without a divergence allowlist. Integer fields accept finite integral JSON numbers such as `3.0`, while strings, booleans, and non-integral numbers remain rejected. A remaining mismatch after these required parity rules is a CCR stop condition.
- `AC-08`: migration must reject a `document.schema_id` that differs from the requested registry identity, or an unsupported source/target version; the recorded identity is the verified identity from the document.
- `AC-10`: every failure path—including malformed Schema registry data—returns exit 1 with a total UTF-8 byte limit, control-character sanitization, traceback suppression, and canary redaction.
