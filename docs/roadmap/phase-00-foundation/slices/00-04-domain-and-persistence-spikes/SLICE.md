## Interfaces and authority

- `src/hermes_pipeline/domain/`: the frozen CounterSpike oracle — initial state strictly `(value=0, revision=0)`; from any `(value=v, revision=r)`, accepting `Increment(delta=1)` transitions strictly to `(v+1, r+1)` and produces the unique domain Event `CounterIncremented` whose payload exactly contains the new `value` and new `revision`; any `delta != 1` returns typed `INVALID_DELTA`, leaves state unchanged, and produces no domain Event; standard library and domain value types only; candidate for retention, non-public.
- `ControllerCommandPort.submit(command: ControllerCommand) -> CommandReceipt`: the accepted Controller external Interface and the **only** Interface the Stage Executor may call; it returns the existing receipt model, including a non-durable `REJECTED`/`INTERNAL_ERROR` receipt with fixed message `persistence unavailable` and `retryable=true` for `SQLITE_FULL` or persistence unavailability; no durable receipt record or partial records are written on that failure path, and raw `sqlite3`, SQLAlchemy, or driver exceptions never cross the Interface; the LangGraph spike graph reaches business state only through it.
- Controller private persistence port: private to `controller`; the spike submit flow evaluates a command against CounterSpike state and commits Inbox, Event, projection, Outbox, and receipt in one SQLite transaction; the port has a deterministic in-memory Adapter and a SQLite spike Adapter; Controller code imports neither SQLAlchemy nor LangGraph nor concrete Adapters nor filesystem code (enforced by import-boundary tests and `architecture check`).
- Stage Executor boundary: the Stage Executor and LangGraph graph code import only domain values and `ControllerCommandPort`; positive and negative import-boundary tests forbid importing the private persistence port, any persistence Adapter, SQLAlchemy, or database files.
- Backup and migration test-helper Interfaces: bounded typed results only; raw driver exceptions, SQL, paths, and database content never reach callers; negative tests prove no traceback, no raw SQL, no absolute path, no database content, and no raw exception text in any output.
- Controller database: one SQLite file for Inbox/Event/projection/Outbox/receipt/lease spike tables; the checkpoint database is a separate physical SQLite file with no shared transaction.
- `SqliteSaver`: LangGraph checkpoint persistence for the spike graph only; local feasibility evidence; never authoritative for business state.
- Dependency surface: SQLAlchemy Core, Alembic, LangGraph, and `langgraph-checkpoint-sqlite` (with the full locked transitive graph, including `sqlite-vec`) exist only in the `dev` group and are importable only from uv development/CI commands; the Hermes plugin entry, `--version`, and the normal runtime path (`src/hermes_pipeline/__init__.py`, `src/hermes_pipeline/cli/__init__.py`, `src/hermes_pipeline/cli/_main.py`, `src/hermes_pipeline/cli/__main__.py`) never import them (regression test).
- Spike evidence artifacts live under `tests/`; the workload, backup, recovery, migration, and replay metrics are captured as bounded test output and recorded in the Execution Report; the workload report contains only the fixed redacted runner profile (OS family, architecture, CI runner label, Python version, `sqlite3.sqlite_version`) plus PRAGMAs and queue high-water — never hostname, username, absolute paths, environment values, tokens, raw exceptions, or database content.
- The Executor may read every tracked file but may edit only the machine contract's permitted paths in the assigned worktree.

## Planning decisions

- Dependency policy (human-approved, ADR-0027 committed in this planning change): `sqlalchemy>=2,<3`, `alembic>=1.19,<2`, `langgraph>=1.2,<2`, and `langgraph-checkpoint-sqlite>=3.1,<4` with their complete transitive shape (including `sqlite-vec`) are development/CI-only feasibility-spike dependencies for Slice 00-04; `[project].dependencies` stays empty; the Hermes plugin entry, `--version`, and the normal runtime path never import them; any future entry into an isolated managed runtime requires a later, separately human-approved ADR and Slice.
- Transaction authority (ADR-0014/0021/0023): the Controller Event Log remains the sole authoritative business history; the Controller database and the LangGraph checkpoint database are physically separate files; no cross-database transaction exists; `SqliteSaver` is local feasibility evidence only and never a business-state authority.
- Domain oracle (reviewer-directed, rework #1 and #2): the spike uses the fixed product-meaning-free CounterSpike — initial state strictly `(value=0, revision=0)`; from any `(value=v, revision=r)`, accepting `Increment(delta=1)` transitions strictly to `(v+1, r+1)` and produces the unique domain Event `CounterIncremented` whose payload exactly contains the new `value` and new `revision`; any `delta != 1` returns typed `INVALID_DELTA`, leaves state completely unchanged, and produces no domain Event; expected-revision conflict handling is the Controller persistence layer's responsibility.
- Port direction (Codex corrective attempt after two Executor reworks): the persistence port is private to the Controller; the accepted `ControllerCommandPort.submit(command: ControllerCommand) -> CommandReceipt` signature is the only Interface the Stage Executor may call; the Stage Executor and graph code are forbidden to import the private persistence port, persistence Adapters, SQLAlchemy, or database files.
- Typed failure boundary (Codex corrective attempt): the existing `CommandReceipt` status/error model carries translated, sensitive-free failure results. `INVALID_DELTA` projects to `REJECTED`/`VALIDATION_ERROR` with `invalid delta`; conflicts project to `CONFLICT`/`CONFLICT` with fixed safe messages; `SQLITE_FULL` and persistence unavailability project to a non-durable `REJECTED`/`INTERNAL_ERROR` receipt with `persistence unavailable` and `retryable=true`. Raw `sqlite3`, SQLAlchemy, or driver exceptions never cross `ControllerCommandPort.submit` or the backup and migration test-helper Interfaces; negative tests prove no traceback, raw SQL, absolute path, database content, or raw exception text in any output; no committed Schema or accepted Interface changes.
- Transaction-failure vs crash evidence (reviewer-directed, rework #1): AC-03 injects exceptions before and after each logical write inside the transaction; AC-05 crashes a real subprocess only at the pre-commit and post-commit durable boundaries and restarts from the same database and WAL; exception injection is never presented as crash evidence.
- Backup policy (reviewer-directed, rework #1): the backup API and policy reject the raw-copy path before any I/O, and a guard or mock proves the implementation only ever calls `sqlite3.Connection.backup()`; no assertion that a raw copy necessarily corrupts is permitted.
- SQLite safety gate (research note, reviewer-directed rework #1): record `sqlite3.sqlite_version` on both required platforms; the exact predicate `>=3.51.3 OR (>=3.50.7 AND <3.51.0) OR (>=3.44.6 AND <3.45.0)` with committed accept/reject vectors is the safety floor; a failing linked library stops the Slice with a Contract Change Request before any spike persistence conclusion is claimed.
- Driver transaction mode (research note): the spike selects and tests one explicit SQLite transaction mode (for example SQLAlchemy `connect_args={"autocommit": False}` or an explicit `BEGIN` event hook); the legacy `sqlite3` default transaction control is never relied on; Alembic `begin_transaction()` is a logical migration transaction and whole-migration rollback atomicity is never promised.
- Workload envelope (reviewer-directed rework #1/#2 plus Codex corrective attempt; phase-plan `R-03`): fixed reproducible envelope — 1,000 accepted commands, 4 producers, one writer, queue capacity 32, command and event payloads no larger than 1 KiB, p95 acknowledged latency `<=2s`, busy count `=0`, WAL high-water `<=16 MiB`, checkpoint/online backup/fresh-process recovery each `<=5s`; the report records a fixed redacted runner profile (OS family, architecture, CI runner label, Python version, `sqlite3.sqlite_version`) plus PRAGMAs and queue high-water; hostname, username, absolute paths, environment values, tokens, raw exception text, and database content are forbidden, proved by a redaction assertion with injected fake sensitive values; a deterministic `SQLITE_FULL` injection returns the specified non-durable `REJECTED`/`INTERNAL_ERROR` receipt without a durable receipt record or partial data and must not exhaust real disk; the envelope is the acceptance boundary and an exceeded limit triggers the replacement-ADR path.
- Offline verification (reviewer-directed, rework #1): the complete offline canonical command set mirrors the exact unchanged commands of `.github/workflows/python-quality.yml`; every spike test is covered by the offline pytest run; the non-offline `unit-check` alone is never the evidence for complete offline verification.
- Code disposition (slices/README 00-04 mandate): only the CounterSpike domain evaluator may be retained as a non-public candidate; persistence, migration, workload, and LangGraph checkpoint spikes are experimental and deleted or rewritten unless Slice 00-07 explicitly adopts them.
- Out-of-scope confirmation: no cross-database transaction, no production service, no Hermes behavior, no real business state machine, no runtime dependency, no remote operation, and no product public API for spike typed failures is part of this Slice; those require their own approved contract and ADR.
- Future implementation allowed paths (revision 7, per this CCR): `pyproject.toml` (dev group only), `uv.lock`, `.python-version`, `.github/workflows/python-quality.yml`, `scripts/check_documentation.py` (revision-7 workflow-policy constants only), `tests/` (including `tests/test_quality_workflow.py`), `src/hermes_pipeline/domain/`, `src/hermes_pipeline/controller/`, `src/hermes_pipeline/persistence/`, `src/hermes_pipeline/stage_executor/`, and `docs/development/compatibility-targets.md`; all other `scripts/`, `.github/workflows/`, `schemas/`, `contracts/`, `src/hermes_pipeline/contracts/`, `src/hermes_pipeline/cli/`, and all accepted planning, review, evidence, and closeout records stay closed unless a Contract Change Request approves otherwise.

## Revision 7 (2026-08-08) — CCR resolution: managed interpreter pin for the SQLite version gate

Attempt 1 under revision 6 stopped with `BLOCKED_CONTRACT`: the managed Windows runtime (CPython 3.12.10) linked SQLite `3.49.1`, failing the exact WAL-reset repair-version predicate (`>=3.51.3 OR (>=3.50.7 AND <3.51.0) OR (>=3.44.6 AND <3.45.0)`). Per the stop condition, no spike persistence conclusion was claimed and a Contract Change Request was submitted. Human decision (2026-08-08):

- **The SQLite predicate is unchanged** and remains an independent per-platform acceptance gate measured via `sqlite3.sqlite_version`; official SQLite fix points are only 3.51.3 and the two named backports, with no 3.49.x relaxation basis.
- **The managed interpreter is pinned to the exact uv-managed CPython `3.12.13` (Astral build)**: `.python-version` = `3.12.13` (no `+`); `python-quality.yml` pins `setup-uv` `python-version: "3.12.13"` and sets job env `UV_MANAGED_PYTHON=1`, forcing uv to use only managed Python installations so a system interpreter with a different bundled SQLite can never satisfy the gate.
- **CI responsibility split**: `documentation-contracts.yml` stays at `"3.12"` — it runs only stdlib-only bootstrap checks and carries no SQLite persistence conclusion, so it is not bound to the source-only `3.12.13` patch. `scripts/check_documentation.py` carries split constants (`REQUIRED_PYTHON_VERSION` 3.12 for the documentation workflow; `REQUIRED_QUALITY_PYTHON_VERSION` 3.12.13 for the quality workflow) and requires `UV_MANAGED_PYTHON=1` in the quality job env; `tests/test_quality_workflow.py` gains a negative test proving a quality job missing the managed-Python enforcement fails.
- **Authorized paths extended for this revision**: `.python-version`, `.github/workflows/python-quality.yml`, `scripts/check_documentation.py` (revision-7 constants only), `tests/test_quality_workflow.py`.
- `docs/development/compatibility-targets.md` records the pin decision and the Windows initial observation (uv-managed CPython 3.12.13 links SQLite 3.53.1); the Linux value is recorded after the first dual-platform CI run with the pinned interpreter.
