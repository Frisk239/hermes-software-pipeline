# Confine Codex and OpenCode to a disposable sealed-tool runtime

**Status: proposed - DRAFT only. This ADR is not accepted. Only a human may accept it, and Slice 00-06 cannot become READY until that acceptance is recorded together with ADR-0029.**

Codex CLI (`0.146.0`) and OpenCode CLI (`1.18.12`) are typed Agent Adapter targets for the 00-06 security spikes. They are external binaries acquired and run only through a disposable sealed-tool runtime; neither becomes a root-project, Hermes-process, or production-runtime dependency.

**Actors and trust root.** "Host" means the privileged Slice 00-06 sealed-tool test runner that invokes `tools_bootstrap.py` and `controlled_e2e.py`. It is not the CONTEXT.md **Host Operator**, not a new Pipeline role, and not a grant of Project authority. "Sandbox Agent child" is the untrusted child under that runner. This decision does not add either name to CONTEXT.md. Git Custodian — the engineering harness or authorized human defined by the operating model — is the out-of-band issuer of the Integration-Candidate snapshot and the three authorization artifacts. The Host is validate-only. This ADR neither requires nor provides cryptographic proof of Custodian identity. Version 1 does not defend against a malicious host administrator.

**Binding decisions versus 00-06 projection.** The binding decisions are: committed runnable identities; no root or production Agent-CLI dependency; Custodian-only resolve/materialize/verify of the Integration-Candidate no-`.git` snapshot; static pre-execution record, then run binding, then single-use gate, then Host validate-only, then provision/probe, then separate observations; observations never authorize; fail-closed unsupported platforms; ordinary PR CI adds no 00-06 workflow; Windows sealed Codex remains `UNSUPPORTED_RUNTIME` until an independently sourced exact Authenticode signer identity is pinned; fuzzy publisher matching is forbidden; Linux Codex sigstore is supplemental; only `opencode-windows-x64` and `opencode-linux-x64` are runnable. The seven CLI flag names, JSON field lists, and file basenames are Slice 00-06 / `tool-lock.json` projections and may change by Slice Contract revision unless those decisions change.

1. **Committed runnable identities.** `tool-lock.json` fixes exact Codex package archives and official SHA-256 values, plus the OpenCode wrapper/platform tarballs and their SRI SHA-512 values. Only `opencode-windows-x64` and `opencode-linux-x64`, selected from locked OS/CPU fields and extracted traversal-safely, are runnable OpenCode identities; the wrapper is not. Linux Codex sigstore is supplemental because no independent verifier is locked. Windows Codex remains `UNSUPPORTED_RUNTIME` for a real sealed probe because the planning record lacks an independently sourced, exact Authenticode signer identity; fuzzy publisher matching is forbidden.

2. **Hard acquisition and child confinement.** Every runnable asset must pass its recorded SHA-256 or SRI before use. OpenCode release archives and `latest.yml` are research-only, and no TOFU, wrapper, system-preinstalled binary, `latest`, `npx`, or auto-update fallback is allowed. Tools install only below the disposable 00-06 state root, never the 00-05 Hermes runtime root. Before authorization, the Git Custodian alone resolves the exact Candidate and exact Integration Candidate plus their tree identities, materializes a no-`.git` controlled snapshot from that Integration Candidate, verifies its source-tree digest exactly equals the Integration-Candidate tree digest, and delivers it as a Custodian-owned read-only validation handoff to Host while exposing it only as the source tree usable by the untrusted Sandbox Agent child. This does not constrain normal repository CI or Custodian Git work before delivery. The Host may only read, inspect, and validate the received handoff; it may not use Git or materialize, copy, transform, mutate, or execute it as a separate source. The child receives state-root-local HOME/XDG/Git configuration and no Git executable or shell-string bypass. `OPENCODE_DISABLE_AUTOUPDATE=1` is fixed and Codex update is denied.

3. **Two-phase immutable Custodian authorization.** The mandatory order before any real binary, provisioning, `--version`, or capability probe is: Custodian resolves Candidate/Integration Candidate/tree identities -> Custodian materializes/verifies the no-`.git` read-only snapshot -> Custodian delivers its read-only validation handoff to Host while exposing it only as the source tree usable by the Sandbox Agent child -> Custodian creates the immutable static pre-execution tool record outside the child snapshot -> Custodian creates the immutable run binding -> Custodian issues the single-use gate -> Host reads, inspects, and validates the handed-off snapshot, record, binding, gate, and seven inputs without separate-source execution -> real provisioning/version/probe -> observations -> cutoff.

   The pre-execution record is at a Custodian-controlled location and read-only to the Host and child. Its RFC 8785 canonical identity is constructed only from static locked inputs: schema version; Planning Base SHA; Candidate SHA and Candidate tree digest; Integration Base SHA; exact Integration Candidate SHA and Integration Candidate tree digest; the verified snapshot/source-tree digest equal to that Integration-Candidate tree digest; full `tool-lock.json` digest; selected platform; selected tool-lock entries; and Custodian origin. It must exclude version output, capability-probe result, any observed date/timestamp, asset-verification result, the run-binding digest, and any runtime or post-execution result. Its RFC 8785 identity digest is `tool_record_digest`.

   The run binding is also created outside the child snapshot. Its RFC 8785 canonical content binds: schema version; Planning Base SHA; Candidate SHA and Candidate tree digest; Integration Base SHA; exact Integration Candidate SHA and Integration Candidate tree digest; the same verified snapshot/source-tree digest; full `tool-lock.json` digest; `tool_record_digest`; Custodian origin; unique run id; issued/expiry timestamps; and a single-use nonce. The single-use host gate carries the canonical run-binding digest. The Host may only read, inspect, and validate the read-only delivered handoff, pre-execution record, binding, gate, and all seven inputs before any process; it has no Git, snapshot materialization, copy, transformation, mutation, or separate-source execution authority. Only then may it provision/verify assets and run version/capability probes. It writes those post-execution results only to a separate observations document under the state root, which references both `tool_record_digest` and `run_binding_digest`; observations never become the pre-execution record and never rewrite the record or binding. Any static identity, Candidate, Integration Base, Integration Candidate, tree digest, source-tree digest, lock, tool-record digest, origin, expiry, run id, nonce, or binding change requires a new snapshot, record, binding, gate, and full rerun. Any runtime-observation mismatch or failed verification/version/probe fails closed. This is the concrete ADR-0018 binding, not a Planning-Base-only assertion.

4. **CI separation and closed Host entry points.** Ordinary PR CI continues to run the existing full offline pytest suite on Windows and Linux; 00-06 adds no workflow. The real-tool runners are standalone Host-runner CLIs, never pytest-collected, and each rejects before process creation if the static pre-execution record, gate, or run binding is absent or invalid. The Host passes exactly the seven mandatory inputs bound by the Slice Contract (state root, Candidate SHA, source-tree digest, tool lock, tool record, host gate, and run binding); the source-tree digest exactly equals the Custodian-verified delivered snapshot/Integration-Candidate tree digest. Selector choice or environment variables are never authorization. `uv run --offline` is Python-offline only; Host bootstrap may fetch only locked assets after snapshot/record/binding/gate validation and before cutoff, then proves fresh offline npm reconstruction.

5. **Vendor facts are not sealed-runtime claims.** As of this planning revision, official OpenAI documentation describes both a native Windows sandbox workflow and WSL2 as an alternative Linux route. That vendor information does not prove project sealed-runtime capability. The project still marks Windows Codex `UNSUPPORTED_RUNTIME` solely because the locked evidence lacks an independently sourced exact Authenticode signer identity. Vendor documentation, immutable artifact/checksum evidence, and dated project probe results are separate registers and must never be collapsed.

6. **Failure closure.** If a platform cannot meet its exact asset rule, lower-privilege or OS-sandbox proof, Custodian-resolved/materialized/verified no-`.git` snapshot plus its read-only validation handoff to Host and exposure only as the source tree usable by the Sandbox Agent child, pre-execution-record/binding/gate validation, or post-execution verification/version/probe result, dispatch fails closed as `UNSUPPORTED_RUNTIME` or `DEPENDENCY_UNAVAILABLE`. The Host may only read, inspect, and validate the handoff; it must not use Git or materialize, copy, transform, mutate, or execute the snapshot as a separate source. It must not downgrade the requirement to a host-installed tool, mutable runtime record, or unbound Integration Candidate.

Any future change that places Codex, OpenCode, or a system-installed Agent CLI in the root project or a production service requires a separate accepted ADR and Slice Contract.
