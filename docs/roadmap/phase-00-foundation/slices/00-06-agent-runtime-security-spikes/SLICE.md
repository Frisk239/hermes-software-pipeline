## Current decisions and hard boundaries

- The committed `tool-lock.json` is the versioned identity and closed-execution-policy source. The adjacent `package.json` and `package-lock.json` remain byte-identical standard npm inputs. The slice-owned `.npmrc` locks audit/fund/update-notifier/ignore-scripts defaults; the Host repeats `--ignore-scripts` and runs only the exact no-audit/no-fund/no-update-notifier npm argv with state-root cache, configuration, HOME, and clean environment, then proves its fresh offline counterpart.
- Node `22.23.2` requires its exact SHA-256 and locked Node release-key fingerprints. `chrome-devtools-mcp@1.7.0` is pinned by the committed npm lock and SRI. Chrome for Testing `151.0.7922.77` has no official checksum and remains experimental/non-sealed; it cannot satisfy a hard integrity gate.
- Chrome DevTools MCP uses only the lock-selected Chrome-for-Testing executable for its OS/CPU and a closed Host-built argv: `--headless`, `--isolated`, explicit executable path, a Host-reserved `127.0.0.1` fixture allow-list, no MCP usage statistics/CrUX, and disabled MCP update check. Remote attachment, channel/profile selection, arbitrary Chrome arguments, and every unlisted option are rejected. `--isolated` is an MCP-managed temporary browser profile, not an OS-isolation claim; the policy does not itself prove OS egress denial.
- Codex `0.146.0` uses checked package archives. Linux sigstore is supplemental. Windows Codex is `UNSUPPORTED_RUNTIME` for a real sealed probe until an approved contract pins an independently sourced exact Authenticode signer identity; fuzzy publisher matching is forbidden. Official OpenAI documentation describes both a native Windows sandbox route and WSL2 as an alternate route; vendor support is not project sealed-runtime proof.
- OpenCode `1.18.12` uses exact runnable `opencode-windows-x64` and `opencode-linux-x64` npm tarballs, locked by OS/CPU selection and SRI SHA-512. `opencode-ai`, release archives, and `latest.yml` are research-only and never establish a runnable identity.
- Ordinary PR CI runs the existing full offline pytest suite and gains no 00-06 workflow. The 00-06 real-tool runners are standalone Host-runner CLIs, never pytest-collected, and reject before process creation if the Custodian pre-execution record, host gate, or run binding is absent or invalid. Test selection is collection hygiene, never authorization.
- Only the privileged Verification Sandbox Host may run `tools_bootstrap.py` or `controlled_e2e.py`. Each receives exactly seven bound parameters: state root, Candidate SHA, source-tree digest, tool lock, tool record, a single-use host gate, and a Custodian-owned immutable run binding. Before any real binary, provisioning, version, or capability probe, the Git Custodian resolves the exact Candidate, exact Integration Candidate, and tree identities; alone materializes a no-`.git` snapshot from that Integration Candidate; verifies its source-tree digest exactly equals the Integration-Candidate tree digest; and delivers it as a Custodian-owned read-only validation handoff to Host while exposing it only as the source tree usable by the Sandbox Agent child. The Custodian then issues a read-only pre-execution tool identity record from only static tool-lock/selected-platform/Candidate/Integration-Candidate/verified-source-tree data, computes its RFC 8785 identity digest, issues the binding, then issues the gate carrying the binding digest. The Host may only read, inspect, and validate the handoff, all three artifacts, and seven inputs; it has no Git, snapshot materialization, copy, transformation, mutation, or separate-source execution authority. Only then may it provision, verify, or probe, and it writes post-execution `<state-root>/tools/tool-observations.json` with both digests plus verification/version/probe/timestamp results. The pre-execution record contains no runtime result or run-binding digest and is never backfilled. Static identity, binding, or Integration Candidate changes require a new snapshot/record/binding/gate and full rerun; a runtime mismatch fails closed.
- Git authority is isolated by the Custodian-delivered controlled source snapshot with no `.git` file or directory: it is a read-only validation handoff to Host and is exposed only as the source tree usable by the Sandbox Agent child environment. The Host may only read/inspect/verify the handoff and has no Git, snapshot materialization, copy, transformation, mutation, or separate-source execution authority. The child has state-root-local HOME, XDG, and Git configuration, and no Git or shell bypass. Repository CI and the Git Custodian legitimately use controlled Git fixtures before any Agent child exists.

## Evidence and safety rules

- Captured output is bounded and redacted by Hermes-side logic. Vendor sanitizers never establish the boundary. Canaries, tokens, paths, usernames, and environment values cannot reach children, logs, artifacts, or reports.
- Capability evidence is recorded per platform as `ENFORCED`, `OBSERVED_ONLY`, `UNSUPPORTED_RUNTIME`, or `NOT_APPLICABLE`. An offline marker is never proof of OS-level egress blocking; a required hard network-deny capability fails closed when it cannot be enforced.
- The controlled E2E drives OpenCode -> Chrome DevTools MCP -> headless Chrome with an MCP-managed temporary profile -> local fixture -> cleanup. `tools/list` never substitutes for E2E evidence.
- A failed boundary, missing host isolation, missing Custodian read-only validation handoff to Host or exposure of the snapshot only as the source tree usable by the Sandbox Agent child, absent pre-execution record/binding/gate validation, Host Git/snapshot materialization/copy/transformation/mutation/separate-source execution, static-identity or Integration-Candidate change without a fresh authorization chain, failed post-execution observation, missing asset identity, closed-argv violation, or unbounded/leaked evidence stops the Slice and requires a CCR.
